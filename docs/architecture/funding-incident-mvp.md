# 확정 후 예치 이상 MVP (#108)

## 확정 정책

2026-10-28 사용자 선택: 확정 근무·출근 유지, 새 지급 보류, 이상 기록과 참여자 인앱 알림. 자동 취소·자리 반환·자금 복구·정산 재개는 하지 않는다. 이미 요청한 지급은 실패로 추정하지 않고 기존 참조의 결과를 계속 조회한다.

## 트랜잭션과 복구

- 검증된 PG 응답에 따른 기존 `PaymentOrderRepository.block` 경로에서 주문 → 예치 잠금 아래에 주문·funding revision별 불변 이상 기록을 저장한다. 예치가 없는 승인 전 오류는 확정 거래 이상 기록을 만들지 않는다.
- 같은 트랜잭션에서 RESERVED/PAYOUT_FAILED 정산을 ON_HOLD(FUNDING_BLOCKED)로 바꾸고 이력을 남긴다. PAYOUT_REQUESTED/PAID와 예치 잔액은 변경하지 않는다. 지급 실행기는 같은 예치 행 잠금을 사용하므로 최초 요청과 보류가 직렬화된다.
- 점주 알림은 차단과 같은 트랜잭션에서 내구성 명령으로 저장한다. 별도 작업자가 이미 확인했거나 늦게 기록된 MatchConfirmed의 근로자 대상도 이상 기록으로부터 수신자별 명령을 만들어 추가한다. 이상 확인 시각과 확정 시각은 공통 `WORK_ATTENDANCE_TIME_ZONE`에서 비교하며, 사건 이후의 새 확정은 과거 사건의 알림 대상에서 제외한다. 근무·매칭 DB를 직접 읽지 않는다.
- 알림 HTTP 호출은 트랜잭션 밖에서 한다. notification-service 내부 API는 공유 시크릿, 고정 명령 ID, 내용 지문, 기존 알림 유일 제약으로 재시도를 처리한다. ACK가 유실돼도 읽음 상태나 알림 수는 바뀌지 않는다.
- 알림 대기 행은 2분 임대 token으로 점유하고 실패 시 재시도한다. 동일 참조·본문을 유지하고 이전 실행의 늦은 ACK는 무시한다. 한 번의 실행은 최대 20건이다.
- 더 높은 funded=true가 와도 이상 이력이나 보류 정산을 자동 삭제·재개하지 않는다. 운영자 읽기 전용 조회는 내부 시크릿으로 보호한다. 재개·계좌 변경·송금 API는 추가하지 않는다.

## 범위와 배포

#132 종료 연동과 #133 지급 실행이 먼저 병합되어야 한다. payment V14를 사용하며 기존 V12와 #133의 V13 이후 순차 배포한다. 이미 배포한 마이그레이션은 바꾸거나 outOfOrder를 켜지 않는다. notification-service의 새 내부 수신 API를 payment 알림 작업자보다 먼저 배포한다. 수신기가 없으면 명령은 실패 후 재시도하며 유실시키지 않는다.

실제 PG 이상 시나리오·지급 중 차단 경합의 공급자 대사, 운영자 권한·감사·수동 재개, 자금 보충/반환, 법적 안내·분쟁 절차, 장기 실패 알림·개인정보 보존 기간은 출시 보강 범위다. 테스트 대역의 성공을 실제 자금 복구로 표시하지 않는다.

지급 실행기 통합 검증은 수취인 조회 중 차단되면 새 지급 명령·요청이 생기지 않는 경합과, 지급 요청 후 차단·응답 유실이 겹쳐도 기존 참조 조회로 성공을 반영하고 재송금하지 않는 경합을 포함한다. 차단 후에도 이미 요청한 지급의 확정 성공은 실제 지급액으로 기록한다.
