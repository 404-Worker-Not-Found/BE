# MVP 사용자 여정 통합 검증 (#137)

## 설계

8개 서비스를 실제 Java 프로세스로 실행하고 HTTP와 Redis Stream을 연결한다. 실행마다 새 MySQL·Redis 컨테이너, 서비스별 DB·계정과 임의의 loopback 포트를 사용한다. 기존 `.env`나 로컬 개발 DB는 읽거나 수정하지 않는다. 종료·실패 시 시작한 프로세스와 전용 컨테이너만 제거한다.

외부 문자·이메일 인증 완료 플래그는 전용 Redis fixture로 준비하고 회원가입·로그인 자체는 실제 auth→member HTTP를 호출한다. 국세청과 PG는 loopback HTTP 대역으로 대체한다. 실제 이메일·문자 전달, 국세청 검증, 토스 결제창·실제 지급·브라우저 연동이 검증됐다고 해석하지 않는다. 실제 지급 실행은 꺼 둔다.

정상 흐름은 가입·로그인 → 비공개 공고 → 결제·예치 → 공개 → 지원 → 수동 선택·수락 → 잠금·예정 근무·채팅방 확정 → GPS 출근·점주 시작·완료 → 이벤트 기반 매칭 종료·정산 예약·상호 리뷰다. 권한 없는 근무 조회, 이른 시작과 잘못된 GPS는 거절되어야 한다.

예외 흐름은 양측 동의 취소 및 자동 노쇼의 근무→매칭→잠금 해제, 외부 취소 이상에 따른 확정 근무 유지·이상 기록·양측 알림 전달·근무 완료 후 정산 보류다. 근무 시간 경계는 격리 DB의 해당 근무 일정 fixture만 조정하며 운영 시간 정책을 완화하지 않는다. 지급·환불 예약액은 실제 공급자 성공으로 위장하지 않는다.

## 실행

Docker, Java 17, Python 3가 필요하다. 저장소 루트에서 `python3 scripts/e2e/mvp_journey.py`를 실행한다. 각 서비스 JAR을 빌드한 뒤 시나리오를 수행한다. 로그 경로와 통과한 단계만 출력하고 토큰·응답 전문은 출력하지 않는다. 실제 PG와 프론트엔드 연결 검증은 별도 단계다.

#137 최초 검증 당시 공고의 `BusinessValidator`는 로그만 남겼다. #140부터 활성 점주의 등록 프로필 ID를 실제 member-service와 대조하고, 다른 점주의 사업장 거절 및 회원/프로필 ID 분리를 검증한다. 과거 24개 검사가 현재 소유권까지 검증한 것처럼 소급 해석하지 않는다.

## 실행 결과 (2026-10-29)

8개 실제 서비스로 명명된 24개 검사를 통과했다. 정상 근무·양측 취소·자동 노쇼·예치 이상을 각각 새 공고·매칭으로 실행했다. 예치 이상 이후에도 실제 GPS 출근·근무 완료가 가능하고 정산은 ON_HOLD가 됐으며, 사건 알림이 실제 notification-service HTTP 수신기로 양측에 전달됐다. 정산 금액은 공고 당시의 서버 계산 전액 예약 기준이며 일정 fixture 이동으로 재계산하지 않는다.

성공한 실행 뒤 전용 컨테이너와 Java 프로세스가 남지 않는 것을 확인했고, 컨테이너 생성 이후 SIGTERM으로 중단하는 별도 검사에서도 전용 컨테이너 2개가 제거됐다. 기존 서비스별 전체 검증은 1,199개 테스트를 통과했다. 이 결과는 위에 명시한 외부 연동·브라우저·소유권 검증 경계를 확장하지 않는다.

## 실행 안정성 보강

외부 명령은 기본 30초, SQL 확인은 10초, JAR 빌드는 15분 제한을 둔다. 명령 timeout은 민감한 인자를 포함하지 않는 오류로 바꾼다. MySQL은 초기화 임시 서버의 Unix 소켓 대신 TCP 준비 상태를 확인한다. 프로세스·로그 정리 실패가 나도 남은 전용 컨테이너와 HTTP 대역을 정리하며, 제거 실패는 컨테이너 이름과 수동 정리 필요 경고 및 실패 종료로 남긴다. 정리 중에는 추가 SIGTERM/SIGINT로 중단하지 않는다.

`python3 -m unittest discover -s scripts/e2e -p 'test_*.py'`로 명령 timeout·인자 비노출·TCP 확인·정리 실패 격리의 5개 검사를 실행한다. 운영 서비스 코드를 바꾸지 않는 스크립트 수정에서는 이 검사와 실제 여정 재실행으로 관련 동작을 확인한다.

## #140 소유권 연결 확장

회원 ID와 점주 프로필 ID가 다른 계정을 만들고, 다른 점주도 가입시킨다. 공고 `businessId`는 본인 회원 조회의 `ownerProfileId`를 사용한다. 정상·취소·노쇼·예치 이상 네 공고에서 다른 점주의 실제 사업장 ID로 생성하면 403이고 공고 수가 늘지 않는지 먼저 확인한다. 이후 본인 사업장으로 기존 흐름을 이어간다. 확장한 실제 여정 30개 검사와 전체 1,218개 서비스 테스트가 통과했다.
