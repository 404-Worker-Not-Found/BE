# 결제 잠금과 Saga 보상 계약

## 현재 범위

payment-service는 공고별 예치 잔액에서 매칭 급여를 잠그고, 확정 Saga 실패 시 예치 가용 잔액으로 반환한다. matching-service의 기존 계약을 그대로 구현한다. 잠금은 Saga 진행 중에도 존재하므로 매칭 확정이나 근무 완료를 뜻하지 않는다. 잠금 해제는 PG 환불과 다르다.

결제대행사, 테스트 자격증명, 예치 시점은 아직 확정되지 않았다. 따라서 이번 구현에는 예치 요청·PG 승인·웹훅·사용자 결제 API가 없다. 예치 행이 없으면 잠금은 409로 거절된다. 테스트에서만 예치 fixture를 넣으며 운영용 임의 충전 API나 성공 stub은 제공하지 않는다. 실제 예치 연동 전에는 이 서비스만으로 매칭 확정을 끝까지 실행할 수 없다.

## 내부 API

모든 요청은 X-Internal-Secret과 1~128자 공백 없는 ASCII Idempotency-Key가 필요하다. 응답은 공통 ApiResponse다. 내부 secret이 누락되거나 공백이면 서비스 시작 단계에서 설정 검증에 실패한다.

| 명령 | 경로 | 요청과 응답 |
| --- | --- | --- |
| 잠금 | POST /api/payments/internal/locks | matchingId, jobPostId, ownerMemberId, workerMemberId, amount, currency → data.paymentId 문자열 |
| 해제 | POST /api/payments/internal/locks/{paymentId}/release | 본문 없음 → 성공 envelope |

ID는 양수, 금액은 양수 DECIMAL(19,2), 통화는 대문자 3자이며 예치 통화와 정확히 같아야 한다. 금액 표현 80과 80.00은 동일 요청이다. 이 저장 정밀도는 통화별 과금·반올림 정책을 확정한 것이 아니다. 실제 PG 연결 전에 지원 통화와 최소 단위 검증을 추가한다.

- 401: 내부 인증 실패
- 400: 요청·명령 키 검증 실패
- PAYMENT-404-001: 해제할 잠금 없음
- PAYMENT-409-001: 예치 없음
- PAYMENT-409-002: 명령 키를 다른 내용 또는 작업에 재사용
- PAYMENT-409-003: 매칭의 다른 활성 잠금 존재
- PAYMENT-409-004: 가용 예치 잔액 부족
- PAYMENT-409-005: 예치 소유자 또는 통화 불일치
- 알 수 없는 DB·서버 실패: 안전한 5xx. 호출자는 같은 명령 키로 재시도한다.

## 데이터와 동시성

- payment_deposits: 공고당 하나의 예치 잔액. 소유자·통화·누적 예치 금액·현재 잠금 금액을 보관한다. 앞으로 PG 검증 완료 후의 원장 반영에서만 예치 금액을 증가시켜야 한다.
- payment_locks: 매칭 시도별 잠금. 외부 matching/job/member ID와 금액·통화 스냅샷을 보관한다. paymentId는 이 잠금 행의 ID다. LOCKED → RELEASED만 제공하며 PG 결제 전체 상태와 구분한다.
- payment_commands: 명령 키·버전 포함 fingerprint·성공 결과 또는 업무 거절을 보관한다.
- payment_matching_slots: 매칭별 직렬화와 활성 잠금 참조. DB 유일 제약도 활성 잠금 중복을 차단한다.
- payment_status_histories: 전이·명령 키·시각. 내부 Saga가 변경 주체다.

잠금 순서는 명령 → 매칭 slot → 예치 → 개별 잠금이다. 다른 매칭이 같은 공고 잔액을 동시에 사용해도 예치 행 잠금으로 초과 사용을 막는다. 예치의 잠금 금액은 항상 0 이상 누적 예치 금액 이하이다. 외부 서비스 테이블과 물리 FK를 만들지 않는다.

업무 거절은 잔액 변경 전에 판단하고 명령 결과를 커밋한 후 HTTP 오류로 변환한다. 잔액 부족으로 거절된 명령은 나중에 잔액이 늘어도 같은 키로 성공하지 않는다. 새로운 시도는 새 키가 필요하다. 인프라 오류는 전체 롤백하므로 재시도할 수 있다. 업무 거절 예외를 금액 변경 이후에 추가하지 않아야 한다.

성공한 과거 잠금 요청을 다시 보내면 해제된 경우에도 원래 paymentId를 반환한다. 해제된 잠금은 보존하고, 새 Saga 시도는 새 키로 새 paymentId를 생성한다. 과거 잠금의 해제를 다시 받아도 현재 잠금이나 잔액에 영향을 주지 않는다. 성공·거절 명령과 이력은 보관 기간 결정 전까지 삭제하지 않는다.

## 후속 작업과 검증 경계

1. PG 및 예치 시점·금액 정책을 정한다. 공고 금액과 소유권을 신뢰 가능한 서버 계약으로 확인한다.
2. 서버가 만든 결제 주문, PG 결제 식별자와 검증 결과를 기록한다. 클라이언트 성공 화면이나 웹훅 본문만으로 잔액을 늘리지 않는다.
3. PG 승인 결과의 주문·금액·통화·상태를 검증한 뒤 중복 없는 예치 원장 반영을 연결한다. 승인 응답 유실과 웹훅 중복도 복구한다.
4. 팀원의 공고 승인·자리 예약 API가 제공되면 실제 서비스 간 지원·수락·실패 보상을 검증한다.
5. 정산·환불을 추가할 때는 해당 상태의 Saga 해제 가능 여부와 잔액 제약을 함께 확장한다.

현재 MySQL Testcontainers 검증은 예치 fixture를 사용한 잠금·해제·동시성·롤백 및 HTTP 계약 검증이다. PG 연동이나 전체 서비스 E2E 검증을 대체하지 않는다.

## 로컬 실행

.env.example의 PAYMENT_*를 개인 .env에 설정하고 공통 내부 secret을 맞춘다. ./scripts/local-run.sh infra 후 ./scripts/local-run.sh payment로 실행한다. HTTP 포트는 8085, 로컬 MySQL 포트는 3313이다. 실제 .env는 커밋하지 않는다.
