# MVP 정산 조회와 지급 실행

관련 이슈: #105. 근무 완료 후 24시간 대기와 잠금 금액 전액 예약은 기존 결정을 따른다.

## 범위와 출시 경계

점주와 근로자는 본인 정산의 금액·상태·지급 가능 시각을 조회한다. 운영자 강제 지급 API나 수취 계좌를 노출하지 않는다. 지급 실행은 기본 비활성화한다. 실제 PG 지급 계약·개인 수취인 등록·KYC·암호화 어댑터가 없으므로 운영 환경에는 성공을 흉내 내는 구현을 넣지 않는다. `PayoutGateway`의 테스트 대역으로 지급 흐름을 검증한다. 활성화 시 어댑터가 없으면 시작 실패한다.

## 실행과 정합성

지급 스케줄러는 자체적으로 스케줄링을 등록하며 다른 복구/이벤트 설정이 꺼져 있어도 `PAYMENT_PAYOUT_ENABLED` 조건으로 동작한다. 실제 지급 어댑터 없이 활성화하면 시작 실패한다.

- 서버에 저장한 근무·잠금·정산 금액만 사용한다. 첫 외부 호출 전에 정산당 하나의 지급 참조·수취인 참조·금액·통화를 영속화하고 PAYOUT_REQUESTED로 바꾼다.
- 수취인 참조 조회 및 PG 호출은 DB 트랜잭션 밖이다. 수취인 등록·계좌 변경은 이 MVP의 범위가 아니다.
- 매칭 slot → 예치 → 원래 잠금 → 정산 → 지급 명령 순서로 잠근다. 최초 지급은 대기 기간 종료·활성 TRANSFERRED 잠금·자금 차단 없음 조건을 다시 검증한다.
- 준비 단계의 수취인 조회 실패·미등록·비활성 잠금은 금액과 RESERVED 상태를 유지하고 UTC 기준 다음 확인 시각·실패 횟수·사유를 저장한다. 기본 5분(`PAYMENT_PAYOUT_PREPARATION_RETRY_DELAY`) 동안 준비를 반복하지 않으며, 아직 시도하지 않은 후보를 먼저 처리해 오래된 실패가 뒤의 정상 지급을 막지 않는다. 이미 요청된 지급의 결과 조회에는 이 준비 대기를 적용하지 않는다.
- lease는 기본 1분(`PAYMENT_PAYOUT_LEASE_DURATION`)이며 실제 어댑터의 요청·조회 전체 타임아웃은 이보다 짧아야 한다. lease와 점유 token으로 이전 실행의 늦은 결과 반영을 막는다. 정산당 지급 명령은 하나이며 재실행에서도 원래 참조·수취인·금액을 유지한다.
- 최초 점유만 지급 요청을 보낸다. 오류·응답 유실·프로세스 재시작 이후에는 기존 참조로 조회만 한다. 첫 호출 전 크래시나 조회의 확정 부재는 REVIEW_REQUIRED로 남기며 자동 재송금하지 않는다.
- 응답의 참조·수취인·금액·통화·provider ID를 검증한다. 확정 성공일 때만 예약액을 지급 완료액으로 옮기고 PAID로 바꾼다. 확정 실패는 PAYOUT_FAILED로 남기며 금액을 풀지 않는다. 진행 중·오류·불일치는 예약액을 유지한다.
- 최초 요청 뒤 자금이 차단돼도 기존 요청 조회는 계속한다. 이미 일어난 송금을 숨기지 않으며 추가 요청은 보내지 않는다.
- #132의 취소·노쇼 연동이 먼저 병합되어 지급 이전 정산을 보류해야 한다. 지급 명령·준비 재시도 스키마는 V13이며 develop에 반영된 V12 이후 정상 순서로 배포한다. 이미 배포한 V12를 수정하거나 Flyway outOfOrder를 켜지 않는다.

## API

`GET /api/payments/me/settlements?beforeId=&size=20`: 최신 ID 내림차순, 최대 100, 다음 페이지는 마지막 ID를 beforeId로 전달한다. 본인의 OWNER/WORKER 역할에 해당하는 필드로만 조회한다.

`GET /api/payments/me/settlements/{id}`: 본인 정산만 반환하고 타인의 ID는 404다. 응답의 시각은 근무 시간대(`WORK_ATTENDANCE_TIME_ZONE`, 기본 Asia/Seoul)다. 지급 명령의 provider 참조·수취인 정보는 반환하지 않는다. `payoutReviewRequired`로 결과 불일치·조회 부재로 검토가 필요한 상태를 구분한다.

## 출시 전 보강

실제 PG 어댑터와 계약 검증, 수취인 동의·등록·KYC·계좌 변경 감사, 수수료·세금, 지급 상태 webhook과 대사, 조회 부재·첫 호출 전 크래시의 운영자 복구, 지급 차단과 진행 중 PG 요청의 경합 대응(#108), 지급 결과 재확인과 지표·알람, 영구적인 준비 실패의 운영자 진단·복구가 필요하다. 불명확한 결과를 실패로 추측하거나 새 키로 송금하지 않는다.
