# 등록 사업장 소유권 연결 (#140)

## 확정한 MVP 정책

2026-10-29 사용자는 점주가 가입할 때 등록한 사업장 1개만 공고에 사용하도록 선택했다. 사업장 추가·선택·양도·공동 소유 기능은 추가하지 않는다. 기존 회원 구조의 점주 프로필 1:1 유일 제약을 사용하고 새 DB 테이블이나 식별자를 만들지 않는다.

공고의 `businessId`는 `owner_profiles.id`이며 회원 ID가 아니다. 프론트엔드는 인증된 `GET /api/members/me` 응답의 `ownerProfile.ownerProfileId`를 공고 생성에 사용한다. JWT의 회원 ID를 사업장 ID로 대신 보내면 안 된다.

## 내부 계약

member-service의 `GET /api/members/internal/owners/{memberId}/business`는 기존 `X-Internal-Secret` 보호 아래 활성 OWNER의 등록 프로필을 조회한다. 응답은 공통 envelope의 `data.businessId`, `data.ownerMemberId`이며 연락처·사업자등록번호·계좌는 포함하지 않는다. 비활성·탈퇴 회원은 `MEMBER-404-002`, 근로자·프로필 없음은 `OWNER-404-001`로 거절한다.

job-service는 JWT 점주 ID로 이 API를 호출하고 응답의 점주 ID와 양의 정수 사업장 ID를 검증한다. 응답에서 확인한 본인 사업장과 요청 사업장이 다르거나 위 404 상태/코드 쌍이면 `JOB-403-001`이다. 연결 실패·전체 호출 제한 초과·인증 오류·알 수 없는 오류·잘못된/과대한 본문·점주 ID 불일치는 `JOB-503-001`로 공고 생성을 중단한다. 응답/헤더 전문은 기록하지 않는다.

조회는 공고 DB 트랜잭션 밖에서 먼저 실행한다. 확인한 뒤 기존 공고 저장 트랜잭션이 계정 장벽을 확인하고 공고·결제 주문 명령을 함께 저장한다. 조회 실패 시 둘 다 저장하지 않는다. 연결·본문 수신을 포함한 전체 호출 제한을 강제하고 redirect를 따라가지 않는다.

## 범위와 배포

새 내부 읽기 API를 가진 member-service를 job-service보다 먼저 배포한다. 수신기가 없거나 연결이 끊기면 공고 생성은 성공으로 간주하지 않는다. `MEMBER_SERVICE_BASE_URL`과 공유 시크릿을 사용하며 기존 local-run과 배포 Compose의 공통 서비스 주소 설정을 유지한다.

기존 공고의 임의 `businessId`는 자동 수정하거나 새 계약의 소유권이 확인됐다고 소급 표시하지 않는다. 기존 데이터 정합성 점검은 후속 작업이다. 이 연결은 서비스에 등록된 프로필의 관계를 검증하며 국세청 상태조회가 법적 대표자 신원을 증명한다는 의미는 아니다.

## 검증 결과

회원 내부 API 4개 검사와 실제 loopback 회원 응답을 사용하는 클라이언트·설정·공고 저장 경계 15개 검사가 추가됐다. 전체 8서비스 1,218개 테스트가 통과했다. 격리된 실제 8서비스 여정은 30개 검사를 통과했고, 회원 ID와 사업장 ID를 분리한 정상 생성 및 네 시나리오의 타인 사업장 생성 거절을 확인했다. 테스트 내부 mock은 서비스 단위 경계에만 쓰며 실제 여정의 소유권 HTTP는 대체하지 않는다.
